### 5.5 跨议题实测：v1/v2 时间戳混排（产品提出，PM 用真 SQLite 验）

**产品的主张**：v1 是定宽 6 位 + `+00:00`、v2 修复后是定宽 9 位 + `Z`，`+`(0x2B) 与 `Z`(0x5A) 字典序不同 → 混合批次会乱序，故 AC-077 迁移要做归一化或改解析比较。

**实测（`/tmp/mix.db`，10 行混合串，`ORDER BY created_at, id`）→ 顺序全部正确**，含三组同刻并列：

```
.123000+00:00(v1)  < .123000000Z(v2,tie)  < .123400000Z  < .123450000Z
< .123456+00:00(v1) < .123456000Z(v2,tie) < .123999+00:00(v1)
< .124000000Z < .130000+00:00(v1) < .130000000Z(v2,tie)
```

**机制**：两种格式都是**定宽**，分数位先逐位比较就已决定先后；后缀 `+` vs `Z` 只在「前 6 位分数完全相同」时才参与比较，而那一刻两个时刻**本来就相等**（并列，谁先都合法）。所以「混排乱序」在定宽前提下**不成立**——不必为它做时间戳归一化，也不必把读路径改成解析比较（省一条改动、避一次性能代价）。

**但混排这件事仍要钉住**：一旦 v1 侧哪天写成变宽分数（如 `.64817` 或不带小数），机制立刻失效。**建议研发在 `TestTimestampsSortChronologically` 里补一条 v1 形态样本**（`...123456+00:00` 与 `...123456000Z` 同刻并列断言），3 行成本，把这条前提变成回归门禁。
